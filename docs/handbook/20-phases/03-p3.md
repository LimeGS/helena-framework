---
title: P3 — Flattening
summary: Unroll an admissible surface into a rectangle a detector can read — and admissible means two axes, not one.
---

A curved sheet sampled directly gives a detector geometry it was not trained on.
P3 unrolls it.

## Before you start

A surface that is **both**:

- `GEOMETRY_CERTIFIED` — the shape is a plausible single lamina; and
- physically `CT_SUPPORTED` or `CT_SUPPORTED_REVIEW` — there is papyrus there.

> **Trap** Both, in either mode. A `GEOMETRY_CERTIFIED` surface is still refused
> if its physical axis is `UNVALIDATED`, which is what every freshly imported
> surface carries. `UNVALIDATED` is waiting for a QC job, not failing one — and
> it is the single most common reason P3 refuses a surface that looks fine.

`allow_unvalidated` waives the **physical** half only, never the geometry half,
and a certification run refuses the flag outright.

## How it is queued

Not through `POST /api/jobs`. `POST /api/flattening/run`, from the Flattening
panel, which forwards `limit`, `dry_run`, `allow_unvalidated`, `sample_id` and
`mission_id`; `surface_id` is accepted by the route, not offered by the form.

> **Trap** It returns 409 if `CX_FLATTEN_STORE` has been emptied. A sheet
> published nowhere is one P4 cannot read; the default is
> `/artifacts/flattened-v1` on the platform's own volume.

A queued run is claimed by `helena-fleet-runner`, the same CPU-only worker
image (`helena-worker-cpp`) that claims P2. `vc_flatten` runs on CPU, so the
default engine never waits on a GPU.

## Fields

| Field | Required | What it is |
| --- | --- | --- |
| `artifact_store` | server-owned | where the sheet is published |
| `sample` | **yes** | must equal the job's immutable sample; refused at command build, on the worker, after the claim |
| `surface_id` | | which surface to flatten |
| `limit` | | how many, in a batch. **Defaults to 5** |
| `allow_unvalidated` | | waives the physical axis; refused in a controlled mission |
| `dry_run` | | list and change nothing |
| `profile` | contract-only | the frozen settings; the panel does not send it |
| `binary` | contract-only | allowlisted to **exactly one** value |

> **Note** `binary` cannot select a flattener — the allowlist has one entry.
> Which engine runs is a property of the **profile**: `vc_flatten` or `lasagna`.
> And `profile` itself is a free string with no allowlist, where `binary` is
> pinned; they are not the same kind of field despite reading alike.

Two profiles ship. `flatten-abf-v1@1.0.0` is the default: `vc_flatten`, ABF++
over an LSCM initialisation, on CPU. `flatten-lasagna-v1@1.0.0` is marked
experimental and not the default: lasagna's own gradient-descent fit, GPU
only by its own profile notes.

> **Trap** Selecting `flatten-lasagna-v1@1.0.0` is refused, not routed. The
> lane's own command builder always invokes `vc_flatten` — `--binary` is
> unconditional — so before this was checked, choosing the lasagna profile
> silently ran `vc_flatten` against a profile file written for a different
> engine entirely, rather than running lasagna at all. The queue now refuses
> the job by the profile's filename and says why. Nothing routes it to a GPU
> worker either: the queue's one P3 lane is claimed by the CPU-only
> `helena-fleet-runner` above and declares no GPU requirement, unlike the
> spiral fitter's P1 lane, which refuses by name on the wrong image.

## Mission scoping

The mission comes from the job row, never from parameters. Queued outside a
mission, a batch works the whole control plane's backlog rather than yours.

## Reading the result

P3 parses its own output as a TIFXYZ before believing the exit code — a habit
worth knowing, because P4 did not for a long time and that is where the "33
files, nothing in them" failure came from. The output is a TIFXYZ, the same
shape as the input: a flattened pixel is not a new coordinate, it is the same
CT voxel the curved surface named at that point, so the coordinate map P4
needs survives flattening by construction rather than by a second map that
could disagree with the first.

> **Trap** The way P3 succeeds and publishes nothing: the **area ratio floor**.
> A sheet whose flattened area is below **0.80** of the source surface area is
> recorded `FLATTENING_REJECTED_AREA` and deliberately **not published** — and
> the batch still exits 0. The job succeeds, the receipt exists, and P4 has
> nothing to consume. Only `FLATTENING_FAILED` returns non-zero.

A source area of zero makes the ratio unmeasurable, and that counts as
`FLATTENED` rather than as a rejection.

A batch's result carries `considered`, a count of outcomes by state, and one
entry per surface in `surfaces[]` — its `state`, `area_ratio`, and, once
published, `artifact_sha256` for the sheet and `source_artifact_sha256` for
the surface it was made from. A sheet is staged first and promoted into the
artifact store only once that succeeds; it is never written to its final
place directly.

The output is a flattened sheet published with its digest.
[P4](#/docs/phases/p4) names it by id, which is what lets the render run on a
different host.

## In the panel

P3's page has a **Sheets** tab beside Run. It leads with four tiles:
**flattened sheets**, **certified surfaces** (P2's count, whatever their
physical QC state), **the backlog** — certified and not yet flattened, minus
the ones still waiting on CT support — and **awaiting CT support**, the
surfaces `allow_unvalidated` exists for.

Below that is a table of every recorded flattening in view, across both
profiles: surface, scroll, profile, state, the area kept, and whether it
published. Anything other than `FLATTENED`, and an area kept under 0.80, are
both marked the same way a number worth a second look is marked.
