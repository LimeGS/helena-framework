---
title: P1 — Segmentation
summary: Recover papyrus as geometry, in TIFXYZ — a seeded grow, or a global spiral fit, one mesh per winding.
---

P1 turns a volume into surfaces. Four backends are registered for it, and only
two actually run here; the other two exist for comparison and have no
executor wired in yet. The two that run fail differently, which is the main
thing to know before choosing between them.

## The backends

| Backend | Method | Status | Note |
| --- | --- | --- | --- |
| VC3D seeded grow | `vc3d-m7-seed-grow@1.0.0` | production | local surfaces from an m7 prior and a seed. Planned by the fleet's own bootstrap, never queued as a job |
| Spiral fitter | `spiral-fitter@0.1.0` | selectable, not default | a global fit through tracks, point collections and a lasagna normal field. Queued as a P1 job on the `spiral-fit` lane |
| ScrollFiesta mesh | `scrollfiesta-m7-mesh@0.1.1` | comparative only | `FAILED_REFERENCE_CONTROL`. Runnable outside the queue; its surfaces are not catalogued until the seam, reference-agreement and flattening gates pass |
| ThaumatoAnakalyptor | `thaumato-anakalyptor@1.0.0` | not integrated | upstream moved it to `deprecated/`; kept in the list because "can the method upstream once used still run" deserves an answer |

**Seeded growth** starts from a point and grows outward, following the sheet
until it loses it. It is local: you get the patch around the seed.

**The spiral fitter** fits a global spiral through the whole scroll at once.
Upstream calls it their most powerful method. They are alternatives, not a
replacement — a spiral fit that defeats itself in a region is a good reason to
grow a patch there instead.

ScrollFiesta and Thaumato are listed so the question "can we run the method
upstream recommends" gets an honest answer, not to offer them as choices: the
panel's New run form queues VC3D only, and asking it for either of the other
two answers `501` — there is no executor in the fleet that would grow with
them, so a task naming one would run VC3D and be recorded under the wrong
method. Their profiles under `framework/profiles/01-segmentation` — three
`hybrid-scrollfiesta-vc3d` versions and two `scrollfiesta-m7-mesh` versions,
all `EXPERIMENTAL_LOCKED` — are adoption gates: a comparison ScrollFiesta
would have to pass, on agreement with VC3D and on flattening, before its
surfaces could be catalogued at all.

## Seeded growth (VC3D)

A grow is not queued the way a fit is. `helena_segment_search_fleet.py
bootstrap` decides which grid cells are uncovered, proposes a seed inside one,
and creates a `segment_tasks` row — the panel's **New run** shells out to that
same command rather than inserting rows itself, so the policy that decides
where to look lives in one place.

**Finding a seed.** A worker's segmentation container starts a seed service —
`vc-mcp`, the MCP seed server — on `127.0.0.1:18080`; its one tool,
`vc_find_seed_candidates`, reads points in a region of an m7 surface
prediction that look like sheet and are far enough apart to be different
places. A worker asks it by default (`--seed-provider mcp`); `recorded` and
`manual` are the alternatives, for a worker replaying a stored proposal or
growing points a person picked instead of searching for them. The service and
the grower are one unit of failure: a worker whose seed service died still
claims tasks and fails them, burning an attempt each time, which is why only
one runs per host.

**Choosing among candidates.** Six planners exist and can be named in a task's
receipt; five are offered from the panel and one is kept only to reproduce
older runs:

| Planner | Kind | Note |
| --- | --- | --- |
| Cost-aware router | router | the fleet's default. Tries deterministic scoring first, then a validated cache, then one model, then a panel of models — and falls back to deterministic if no provider answers |
| Deterministic | deterministic | scores candidates by cell volume and clearance, skips a recipe that already failed in this region |
| Deterministic (history blind) | deterministic | the same scoring with history ignored — the control arm that shows whether reading history changes anything |
| LLM agent (OpenCode) | agent | one model decides, in a disposable project directory |
| Panel of LLM experts | panel | several models propose, one judges — the most expensive lane |
| LLM agent, retired v1 packets | agent | kept only to reproduce runs that used the older packet schema; not offered |

**Task identity.** A task is identified by the CT volume it reads
(`source_snapshot_id`), the grid version, the cell, and the policy version. The
tuple is unique: asking for a cell that already has a task under the same grid
and policy is deduplicated rather than duplicated, so re-running the same
bootstrap command is safe. Growing a lower-ranked m7 candidate over ground the
first one already covered is a different question and needs a new
`policy_version` to be asked. The bootstrap's own defaults are a grid step of
2048 voxels, a query radius of 64, a clearance of 256, grid version
`ct-l0-grid-2048-v1`, policy version `ink-blind-v1`, and up to 24 tasks per
sample per call.

**Claiming and leasing.** Every claim on the control plane uses `FOR UPDATE
SKIP LOCKED` with a hashed lease token, so several hosts can poll the same
queue without claiming the same row twice.

**Two states worth telling apart.** A task ends in many states; these two are
opposites and easy to confuse from the name alone.

- `NO_SEED` — none of the proposals survived. The Coverage tab splits this in
  two: candidates never proposed at all (the search returned nothing), and
  candidates proposed and then removed by a screen. The named screens are
  `NO_M7_CANDIDATES` (nothing above the m7 threshold in that box) and
  `CT_MATERIAL_SUPPORT_REJECTED` (the prediction proposed a point and the raw
  CT has no material there); anything else reads as candidates that were fine
  but too close to ground already covered — the fleet re-treading, which is
  good news wearing a failure's label. `NO_SEED` names the screen that removed
  the proposals; it does not establish that no physical surface is there.
- `QC_PENDING` — the opposite outcome: a surface was produced and is waiting
  on [P2](#/docs/phases/p2)'s geometry gate.

**Seed probes.** A closed-loop layer beneath the planner, not a replacement
for it: bounded deterministic micro-growths compared before the canonical
grow runs. Three modes — `off`, `shadow` (records the comparison, canonical
seed unchanged) and `select` (lets an unambiguous winner steer Cost-aware or
Deterministic v2; ties stop for human review rather than guessing). A worker
must start with `--seed-probe-support` to claim probe-required tasks; an older
or unvalidated host cannot pick one up silently.

**Growth profiles**, under `framework/stages/01-segmentation/fleet/profiles`:

| Profile | Mode | Note |
| --- | --- | --- |
| `vc3d-m7-growth-v1` | canonical | four parameters (`generations` 20-45, `step_size` 12-24, `min_area_cm` pinned 0, `use_cuda` pinned false). Left byte-identical because a frozen plan binds its sha256 |
| `vc3d-m7-growth-v2` | canonical | the same bounds, plus `inpaint`, `skip_overlap_check` and the resume group (`rewind_gen`, `resume_generations`, `resume_opt`) that v1 could not reach |
| `vc3d-m7-probe-v1` | noncanonical | micro-growth (10-20 generations) used only to discriminate seed candidates before a canonical grow; not a canonical surface even when it certifies |
| `vc3d-real-ct-smoke-v1` | canonical | a fixed smoke-test envelope |

## What the spiral fitter reads

| Input | Where it comes from |
| --- | --- |
| Umbilicus | **human annotation.** Not in any bucket; it is uploaded, not fetched. |
| Tracks | fetchable, staged for you |
| Lasagna normal volumes | fetchable OME-Zarr, one level, staged into a per-scroll cache |

> **Trap** The umbilicus is the input that stops a first run. It is
> hand-annotated work — ours came from Aleksei Drobkov and bruniss, across
> thirteen scrolls — so a job that assumes it will be downloaded fails at the
> input survey. That is the cheapest place it could fail, which is why the
> survey exists.

The staging step distinguishes **an absent chunk** from **a network failure**,
and never retries a 404. Those are different problems and a run that conflates
them retries forever against data that is not there.

## Fields

| Field | Required | What it is |
| --- | --- | --- |
| `profile_id` | **yes** | `spiral-fitter-v1@0.3.0` is the only value this lane accepts |
| `artifact_store` | server-owned | where the windings are published |
| `scroll_name` | yes | what the fitter calls this scroll internally |
| `dataset_path` | yes | the staged dataset root |
| `z_begin`, `z_end` | yes | the slice range to fit |
| `voxel_size_um` | yes | the scale, from P0 |
| `spiral_outward_sense` | | `CW` or `CCW`; a property of the scroll. The profile defaults it to `CW`, and the wrong one reverses the fit |
| `random_seed` | | the optimizer's seed |
| `normal_zarr_group` | | which pyramid **level** of the normal volumes to read; a digit string |
| `lasagna_scale` | | the **divisor** the shape check uses. Derived as `2 ** normal_zarr_group` only if you moved the volume name or the group; otherwise it stays at 4 |
| `lasagna_volume_name` | | a template that **must** carry `{array}`, may not contain a slash, and may carry no other brace |
| `tracks_file` | | a bare `.dbm` filename, not a path |
| `run_tag` | | a label that reaches the receipt |
| `dry_run` | | resolve the profile, bind the scroll, survey the dataset, rewrite and read back the fitter — and stop before the fit |

> **Cost** A whole-scroll fit is hours of GPU time, and every input mistake
> costs the whole of it. Fit a thousand slices first.

## How the scroll is selected

This is worth knowing because it is unusual. Upstream's `fit_spiral.py` is a
research script, not a tool: it has no argparse, and the scroll is chosen by six
**module-level constants** assigned at import — `dataset_path`, `scroll_name`,
`z_begin`, `z_end`, `voxel_size_um`, `spiral_outward_sense`. None of them is one
of the 105 keys its config accepts.

So Helena rebinds them: it stages a private copy of the script and rewrites
**twelve** module-level assignments — the six scroll constants, the four
dataset-path templates, and the two layout literals the lasagna shape check
reads — reading each one back after the rewrite, and recording the digest of
both the original and the result. Selecting a scroll is a source rewrite, and
the receipt says exactly which source ran.

Settings, as opposed to the scroll, go through the one interface the script does
have — a JSON object whose keys are validated against upstream's own list before
a GPU is claimed, rather than raising deep inside a run that has already paid
for one. Those overrides come from the **frozen profile**, not from the job:
`random_seed` is the only setting a request can move.

## Refusals worth knowing before you spend a GPU day

- **`z_end <= z_begin`** is refused at enqueue, as is a `spiral_outward_sense`
  outside `CW`/`CCW`.
- **The lane needs the `helena-villa-python` image.** An ordinary GPU worker
  will not claim the job; the row sits `pending`, looking like a stuck queue.
- **The dataset must be staged first.** `stage_spiral_dataset.py` is a CLI step
  you run once per scroll — there is no panel route — and a job pointed at a
  directory with no `SPIRAL_DATASET.json` refuses at the input survey.
- **Register the scroll's source snapshot first.** Without one the run refuses
  *after* the fit has finished, at registration, and the meshes sit on the
  worker unregistered. With the store or the database absent it is worse: the
  run exits **0** as `FITTED_NOT_REGISTERED`, with the meshes stranded.

> **Trap** The four point-collection inputs are **optional**, and their absence
> is not a refusal — one line to stderr and the fit continues. Without
> `abs_winding.json` the windings are **relative**: no surface can be said to be
> the nth turn of the scroll from the fit alone.

## Reading the result

One TIFXYZ per winding, each registered as a surface. That is what makes this a
P1 backend at all: it produces the same artifact seeded growth does, so it
enters the same certification gate rather than a parallel one.

The test the walkthrough gives is the right one: **continuous horizontal and
vertical fibres**, and a mesh that stays on one sheet. You cannot see the second
by looking, which is what [P2](#/docs/phases/p2) is for.

> **Note** A certified winding is still not admissible downstream. Every
> registered winding gets `physical_qc_state: UNVALIDATED`, and P3 needs a
> CT-supported verdict as well as a certified geometry. Certification is one of
> the two gates, not both.

## The panel

P1's Mission view carries six tabs: **Runs**, **Segments**, **Coverage**,
**Profiles**, **New run** and **Import surface**.

- **Runs** lists tasks and attempts: when it started, scroll and cell, state,
  what it produced, area, QC, how long it took, backend and worker.
- **Segments** lists every surface the mission can see, grown or imported, with
  one row per surface:

  | Column | What it shows |
  | --- | --- |
  | Made | when the surface was created |
  | Surface | its id |
  | Scroll | which sample it belongs to |
  | Origin | `GROWN_HERE`, or `IMPORTED` for everything else. An imported row's tooltip carries its `source_catalog` — a VC3D patch someone grew elsewhere and uploaded, or a surface pulled from a public catalogue |
  | Area cm² | measured area |
  | CT support | `physical_qc_state` — `UNVALIDATED` until a CT-material check has run, then `CT_SUPPORTED` or a rejection |
  | Geometry | `geometry_qc_state` — P2's verdict, or `UNMEASURED` if nothing has run yet |
  | Lamina | whether the CT resolves one sheet under this surface or two welded together — a question geometry certification does not answer on its own |
  | Seeds | seed agreement: paired, unpaired (one seed, no error bar), or the override that never took (which reads as perfect reproducibility and is the one flagged red) |
  | Review | a person's opinion — Approved, Defective, Reviewed or Inspect — kept apart from P2's verdict on purpose |
  | VC3D | a link to the volume, the surface, the frame and the `vc_grow_seg_from_seed` command, plus a button that opens three orthogonal CT slices through the surface |

- **Coverage** reports per grid, not per scroll: cells attempted, `NO_SEED`,
  and cells that produced a surface — the hit rate, because a surface count
  alone rises the same whether the fleet is finding new ground or re-treading
  old.
- **Profiles** lists every profile declared for this stage: the growth
  envelopes above, the spiral fitter's three versions, and the comparison and
  campaign policies that are frozen but not runnable from here.
- **New run** queues a VC3D grow through the bootstrap described above. Asking
  it for the spiral fitter answers `409` and points at the P1 job queue
  instead; asking for ScrollFiesta or Thaumato answers `501`.
- **Import surface** registers surfaces this fleet did not grow — a folder of
  VC3D patches, or a public segment — each with a bounding box and a hash, so
  the catalogue has a record rather than a claim. They are always `IMPORTED`,
  never `GROWN_HERE`.

## Traps

> **Trap** A fit that produced meshes is not a fit that worked. The failure mode
> that matters — crossing from one lamina to the next — looks like a clean
> surface until something measures it.

> **Note** A seed that does not take produces two identical fits and a seed
> agreement of zero, which reads as perfect reproducibility. Helena resolves the
> seed's key name from the script rather than guessing it, because this is the
> one metric in the framework where the failure disguises itself as the best
> possible result.
