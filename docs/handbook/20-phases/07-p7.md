The phase that produces the artefact a human actually looks at.

## Before you start

A P5 job that succeeded and whose map is [live](#/docs/phases/p6). P7 reads
the map from wherever it was published — usually another worker — rather than
expecting it locally.

The contract declares P7 gated on P6, and that gate is enforced by the queue,
not by the tool underneath it: naming `map_path` is refused unless the receipt
beside it records `ALIVE`, and naming `screening_of` is refused unless that P5
job's own liveness verdict is `ALIVE`. Call the vetting-card runner directly,
outside the queue, and nothing checks either. The bbox has no producer of its
own in this pipeline either — it is a human claim, and P7 does not vouch for
where it came from.

## Naming the map: exactly one of two ways

This is the rule people hit first, and the queue states it as a refusal rather
than guessing:

- **`screening_of`** — the id of the P5 job that produced the map. The worker
  fetches it from wherever it was published, which is usually another machine.
  Naming it this way **also requires both digests**:
  `probability_map_artifact_sha256` and `probability_map_manifest_sha256`, each
  64 hex characters. A named screening without exact identity is refused.
- **`map_path`** — a file this worker can already see. For a map you produced
  outside the pipeline.

Naming both, or neither, is refused with that sentence. There is no default: a
screening whose subject was inferred is a verdict about something nobody wrote
down.

## Fields

| Field | Required | What it is |
| --- | --- | --- |
| `bbox` | yes | the region, as `x0,y0,x1,y1` |
| `px_um` | yes | the scale of that region |
| `screening_of` | one of two | the P5 job id |
| `probability_map_artifact_sha256` | with `screening_of` | 64 hex |
| `probability_map_manifest_sha256` | with `screening_of` | 64 hex |
| `map_path` | one of two | a map this worker can see |
| `render_cell_px` | | how large a cell renders |
| `roi_receipt_sha256` | | binds the region to a receipt |
| `out_dir` | | where the card and the verdict land |
| `surface_id` | | which surface this is about |

The runner reads a `.npy` float map or an 8-bit `.png`, and nothing else.

The form the panel draws for this phase is served, not hand-kept: `GET
/api/phases/P7/parameters` returns this same field list from the queue's own
schema, so a field added to the queue cannot go missing from the browser.

## What the vetting card checks

The runner is [vetting-card](https://github.com/LimeGS/vetting-card), vendored
at `framework/vendored/vetting-card` (`vet_map.py`). It is arithmetic over the
one claimed bbox, not a model, fit on 324 labelled windows from official
Scroll 1 / PHerc 0139 maps and externally validated on 96 Scroll-4 windows.

One whole-map gate runs first and can stop the tool before it reaches a
verdict at all:

| Check | Asks | On failure |
| --- | --- | --- |
| `render_family` | does the map look like the raw ink-detection output the checks below were calibrated on? | the tool errors out — "cannot evaluate", not a verdict |
| `degenerate` | is the bbox blank, saturated, or the whole map constant? | `overall.pass` is `False`; the three checks below are skipped |
| `letter_energy` | band-pass energy at the letter length scale, relative to the bbox's own variance | must pass |
| `structure` | fraction of the bbox covered by letter-scale connected components | must pass |
| `contrast_bimodality` | is the bbox bimodal in brightness, the way ink and background are? | must pass |

`overall.pass` is `letter_energy AND structure AND contrast_bimodality`, and
that boolean is what a queued job records — `PASS` or `FAIL`. A `FAIL` is not
a failed job: refutation is as much the tool's intended output as a pass is,
so the job still succeeds. No priority review runs without a hash-bearing card
and its input, and a green card does not mean confirmed ancient text — it
means the bytes survived a first automated round of refutation.

## Reading the result

Two files, in `out_dir`:

- **`verdict.json`** — the adjudication, as data.
- **`VETTING_CARD.md`** — the card. It is a **Markdown document**, not an
  image: the region's measurements, the thresholds that were applied and the
  chain behind them, written so it can be read in a review and quoted in one.

## In the panel

P7's page has three tabs: **Screening**, **Profiles**, **Run**.

- **Screening** is a separate, interactive tool, not the queued job above: a
  strict text screen over the whole map, with every threshold on the controls.
  The default gate is at least 10 candidate shapes and at least 2 qualifying
  rows of at least 4 shapes each; its verdict is `PASSES_STRICT_SCREEN` or
  `DOES_NOT_PASS`, and it carries the same caution — passing it is not a
  reading. See [Screening, Coverage and Compare](#/docs/panel/screening-and-coverage)
  for the tool itself. Until a run has a probability map, the tab reads "no
  run has a probability map to screen".
- **Profiles** lists whatever sits under `framework/profiles/04-validation`.
  Today that is two CT-fibre surface-QC profiles built for a different
  adapter; they configure surface geometry QC, not the vetting-card checks
  above. The two share a stage directory, not a purpose.
- **Run** queues the vetting-card job this page describes.

The phase's tiles: **maps available** and **runs screenable** count what
there is to screen — every probability map found, whether from a legacy run
or an `ALIVE` P5 job, and how many runs or jobs carry at least one.
**Adjudications succeeded / failed / queued** are queue outcomes, whether the
job ran to completion. **Adjudications passed / refuted / without verdict**
are the claim outcome read out of each succeeded job's own `verdict.json` —
`PASS`, `FAIL`, or (in practice, a job recorded before this field existed)
neither.

## What a verdict means

The criterion is the Scroll Prize's own and Helena does not replace it:
coherent rows aligned with the papyrus fibres, and at least ten visible
legible letters in about 4 cm².

> **Note** The platform will never tell you a map contains text. It tells you
> the map is live, what it came from, and whether runs of it agree. The reading
> is a person's.

## Traps

> **Trap** Do not adjudicate a region a model was fine-tuned on. A detector
> trained on the area you intend to claim will find letters there. Surfaces in
> the discovery namespace are marked non-canonical for exactly this reason.

> **Trap** The strict screen and the vetting card are not the same claim, and
> neither stands in for the other. The screen counts candidate shapes and rows
> across the whole map; the card is the calibrated check against the one bbox
> you are claiming.

## Where it runs

`helena-ink-0`, on the `helena-worker-gpu` image — the same worker that runs
P4 and P5. See [deploys](#/docs/operations/deploys) for the rest of the fleet.
