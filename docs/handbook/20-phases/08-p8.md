title: P8 — Reconstruction
summary: Put certified surfaces back together: merged TIFXYZ surfaces, measured wrap order, mesh relations.

Three lanes, three different questions about how pieces of a scroll relate.

## Lanes

| Lane | Question | Produces |
| --- | --- | --- |
| `vc3d-tifxyz-merge` | do these surfaces form one larger sheet? | a merged TIFXYZ and its lineage |
| `column-atlas` | which wrap sits at what radius, in what order? | a measured wrap order |
| `mesh-relations` | how do these meshes relate spatially? | a relation set |

`column-atlas` measures the physical reading order from the public meshes; it
does not render plates. Composing the atlas itself — the page images a reader
looks at — is P9's job, and it consumes this lane's output.

All three declare `gpu_required: false`. That is the routing fact worth knowing:
the TIFXYZ merge is CPU and high-memory work, so it must be **claimable by a
worker without a card** — otherwise it queues behind renders for a resource it
does not use. None of them pins a runtime image; any worker carrying the VC3D
toolchain can take one.

## Fields

**`vc3d-tifxyz-merge`** requires all seven, and refuses without them:

| Field | What it is |
| --- | --- |
| `artifact_ids` | the certified TIFXYZ artifacts to merge, as JSON |
| `rows` | the surface layout, as JSON |
| `reference_artifact_id` | which surface the others are placed against |
| `ransac_seed` | the fit's seed |
| `anchor_cap` | how many anchor points per surface the blend keeps; 0 keeps every one |
| `strip_cols` | how wide a column-block the blend splits the merge grid into; 0 blends the whole grid in one shared pass |
| `artifact_store` | where it publishes — filled by the deployment |

**`column-atlas`** and **`mesh-relations`** require `scroll` and `out_path`.
`mesh-relations` also takes `subsample` and `work_dir`.

> **Note** `ransac_seed` is required rather than defaulted, and it is the
> difference between a merge somebody can check and one they can only admire. A
> RANSAC fit with an unrecorded seed is not reproducible even by the person who
> ran it.

## Reading the result

A merge records a **routing receipt** that is re-derived from the measured area
rather than trusted from the document that arrived with it. A merged surface
under the area floor never gets a claimable job — it is recorded and left alone
rather than entering a pipeline that would treat it as a sheet.

## Traps

> **Trap** A merge is only as good as its inputs' certification, and passing
> P2 on the inputs is not the same as certifying the merge. The merge job does
> re-run geometry certification on the merged output and re-checks every seam
> the layout declared — anchor count, RANSAC inliers, overlap on both sides —
> and refuses if either fails. What it does not do is check a pair of surfaces
> the layout never named as neighbours: those are only compared for a physical
> collision, and that check is advisory, not a refusal, unless the deployment
> turns it on. In one prior reconstruction two segments the layout never
> paired passed within tens of micrometres of each other — closer than
> papyrus is thick — while every surface involved was geometry-certified and
> every declared seam had passed.

> **Trap** `mesh-relations` is registered for the shape of the interface, not
> because it runs. Its declared runner,
> `framework/stages/05-reconstruction/scripts/evaluate_r6_direct_geometry.py`,
> is an offline calibration tool that takes a different command line entirely
> — a topology graph, ray casts, a ground truth file and a sample file, not a
> scroll name — and no assembler for measured segment relations exists in the
> repository yet. Queueing this lane is refused before a worker ever claims
> it, with a message naming why.
